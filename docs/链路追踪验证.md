# OpenTelemetry 链路追踪

网关通过 OTLP HTTP 将 span 导出到 Compose 中的 Jaeger。入口接收标准 `traceparent` / `tracestate`，MCP 与 REST 下游 HTTP 请求自动透传追踪上下文。

## 观察一次调用

打开 http://localhost:16686，选择服务 `mcp-gateway`。调用响应的 `X-Trace-Id`（REST 响应也包含 `trace_id`）就是 Jaeger 的 trace ID，与 PostgreSQL 的 `tool_calls.trace_id`、`audit_logs.trace_id` 一致。

- REST 工具：请求入口 → `tool.invoke` → HTTP 下游请求。
- 原生 MCP 工具：请求入口 → `tool.invoke` → `mcp.tools/call` → HTTP 下游请求。
- HTTP 失败、MCP `isError`、工具执行错误和入口 panic 标记为错误。
- 入口 span 记录用户 ID、角色、工具 ID、token 估算与成本；不采集 JWT 或完整调用参数。下游 HTTP span 覆盖响应体读取时间。

原有 `X-Trace-Id` 请求头作为 `app.request_id` 属性记录；开启追踪时响应与数据库采用真实 OpenTelemetry trace ID。需要继承上游 trace 时，应发送 W3C `traceparent`。

`OTEL_EXPORTER_OTLP_ENDPOINT` 支持 `jaeger:4318`、`http://jaeger:4318` 或带 `/v1/traces` 的完整地址。留空时仍生成和透传 trace ID，但不导出。外部服务需要自行启用 OpenTelemetry，才能在同一 trace 中增加它自己的服务端 span。

## 重复验收

在项目根目录使用 PowerShell 7：

```powershell
docker compose up --build -d gateway
./tools/verify-tracing.ps1
```

脚本支持 `-Username`、`-Password`、`-BaseURL`、`-JaegerURL`。它验证 REST 成功调用、原生 MCP 成功调用、HTTP 200 的 MCP 工具错误、下游 HTTP 失败四种场景，检查 span 父子关系、远端父 span 继承以及数据库 trace ID 关联。结束后仅删除本次生成的调用与审计记录；Jaeger 中的诊断 trace 保留用于查看。

2026-10-14 的 Docker 联调：四个场景均通过，REST 调用包含 3 个 span，原生 MCP 调用包含 4 个 span，3 条调用记录及 4 条审计记录的 trace ID 均与 Jaeger 一致。Go 测试另覆盖下游 traceparent 透传、响应体完成才结束 span、连接失败、入口权限错误、panic 与无导出器时的本地追踪。
